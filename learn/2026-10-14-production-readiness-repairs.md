# Make dashboard actions verifiable and recoverable

> 2026-10-14 · Audit and repair the public pages and every dashboard, then verify available live customer access.

## In short
The repairs connect dashboard controls to current server permissions, exact payment amounts, and durable recovery records. They also make loading, failure, approval, and refund states visible so a page cannot imply that an unfinished operation succeeded.

## What changed
- `apps/api/src/routes/auth.routes.js` and `middleware/auth.js`: bind MFA to the preceding password step and require current sessions and memberships.
- `apps/api/src/lib/money-amounts.js`, payment routes, and recovery libraries: validate integer kobo, bind provider receipts, and prevent duplicate effects.
- `apps/api/src/routes/company.routes.js` and `admin.routes.js`: require contract approval, preserve account roles, and provision company wallets transactionally.
- `apps/api/src/migrations/032_private_database_access.sql`: restrict direct database access while preserving backend and approved public catalog access.
- Dashboard, auth, and shared web components: repair customer card/PIN/refund states, company switching, partner staff controls, forms, responsive dialogs, and retry behavior.
- `apps/web/app/layout.tsx` and licensed local fonts: remove the build's dependency on downloading Google Fonts.
- The collapsed manifest below names every changed source, test, configuration, license, and documentation file.

## How it works
1. A request verifies its current caller, organization, and resource ownership.
2. Monetary inputs become bounded integer minor units. The server checks the original quote and authoritative provider evidence.
3. Database transactions lock relevant state and commit ledger entries, operation status, and audit records together.
4. Retries reuse durable operation identities. Uncertain provider outcomes stay recoverable instead of being blindly repeated.
5. The UI shows the resulting state, disables unavailable actions, and offers an appropriate retry or Support path.

## Why it's built this way
Existing membership, wallet, and admin verification mechanisms remain the source of truth. A frontend gate improves the experience; the server gate decides access. Database locks and uniqueness protect multiple workers, where an in-memory lock would be insufficient. Small stacking changes fix intercepted Sign Out clicks without changing logout logic.

## The concept worth knowing: idempotency
Think of collecting one parcel using a numbered receipt: showing the same receipt again must not release another parcel. Here, an operation key is bound to the caller and payload, and its durable record prevents a repeated request from creating another money movement. Provider verification and database atomicity are still necessary; a key alone cannot prove that money arrived.

## Watch out for
The local API suite passed 1,016 cases with two credential-dependent skips. Browser checks cover all known local page routes and all 12 live customer routes; they do not cover every possible state. Live funding, station labels, and Sign Out still use earlier behavior. Provider sandbox tests, production database permissions, legacy financial reconciliation, runtime configuration, and qualified human review remain release requirements. No real payment or identity submission was made.

2. What if the provider charged successfully but the response timed out?
   <details><summary>Answer</summary>Keep an uncertain durable record and reconcile authoritative provider evidence. Blindly starting another charge can duplicate the effect.</details>

3. Why can a dialog with a larger z-index still receive no clicks?
   <details><summary>Answer</summary>Its parent's stacking context can sit beneath another layer. The customer account menu and sidebar needed the correct parent layer, verified with actual browser hit tests.</details>
