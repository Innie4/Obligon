# Dashboard release deployment

Apply migrations 020–031 with the repository migrator before serving this release. Back up production first and deploy the API and web together. Migration 019 remains part of fresh installs; 020 resets its unsafe watermarks and quarantines ambiguous historical periods. Historical paid rows with destroyed amounts require reconciliation against processor statements; the application deliberately does not guess them.

Configure Flutterwave checkout, transfer funding, verified webhooks and registered collection subaccounts; Sudo API credentials, debit/credit account IDs and `CARD_IDENTITY_KEY` (32 random bytes as 64 hex characters); production Supabase Auth/storage; and real email/SMS delivery. Rotate the identity key only with an explicit re-encryption migration. Missing issuer configuration fails closed rather than producing fabricated cards.

Migrations suspend legacy settlement subaccounts without an exact bank link. Partners must re-add their bank account and admins verify it before direct checkout is available. Each bank has an immutable destination; changing the default cannot rewrite earlier fuel orders. The automatic transfer scheduler uses verified default bank accounts, while direct fuel checkout requires the bound active collection subaccount.

Run `pnpm config:check`, the production web build, and `pnpm test:api` / `pnpm test:web`. Integration suites additionally use `OBLIGON_TEST_DATABASE_URL` pointing to disposable localhost PostgreSQL. Card issuer integration checks use `TEST_DATABASE_URL` and mocked external APIs. Never aim tests or seed commands at production.

For free local OTP tests select `EMAIL_PROVIDER=local`, `SMS_PROVIDER=local`, and `LOCAL_OUTBOX_PATH` outside public/static directories. Messages expire after ten minutes and the outbox is bounded. Local delivery and explicit payment simulation are rejected in production. Production browser bundles must omit `NEXT_PUBLIC_ENABLE_DEMO_LOGIN`.

Customer first paid subscription starts after admin card approval; renewals use verified payments and one-month periods. Partner operations require an active paid catalog plan, with advanced reports restricted by the catalog. Receipts, support, bank setup and subscription renewal remain available for inactive accounts. All paid customer tiers receive the full approved station discount. At ₦10,000 base and 10%, the checkout charges ₦9,000, records ₦1,000 for Obligon and ₦8,000 partner revenue. Processor fees are separate and require live statement verification.

Direct fuel payments use Flutterwave split settlement and never enter automatic wallet transfer accrual. Wallet purchases atomically debit the fuel wallet and accrue net revenue for completed business months. Transfer timeouts retain reserved funds and reconcile the immutable merchant reference without submitting again. Admin Support & Settlements exposes uncertain transfers, historical accounting exceptions and paid fuel orders that require original-payment refunds. Confirm live processor settlement and refund behavior with an authorized small transaction before accepting production payments.

Physical delivery, biometric authorization and manual payouts remain explicitly coming soon. Admin overview, companies, applications, disputes, staff and reports now load backend records. Public intake, station publication, delivery and redacted activity have a dedicated admin operations console. Company dashboard work beyond the customer/partner scope remains separate.

### Nearby customer stations

Customer Stations accepts a consented device location (updated as it changes) or manual latitude/longitude. The API validates coordinate pairs and ranks all active stations by straight-line distance before returning the nearest 50. Missing customer coordinates produce no guessed distances; stations without usable coordinates follow located stations. The view refreshes every 30 seconds while visible and when focus returns. Search and fuel filters preserve that distance order.

Partner registration retains station address, city and available fuels. Partner Station Profile requires exact latitude/longitude when saving, validates geographic bounds, and saves fuel names as an array. Partner verification and station publication are separate approvals. Station publication requires a verified organization and confirmed coordinates; pending stations remain unpublished. Migration 025 removes the hardcoded Lagos coordinate defaults and permits unknown locations. Existing coordinates are preserved; entries at the exact former default pair need partner confirmation before distance ranking. Existing stations with missing or unconfirmed coordinates need their partner to complete Location Details.

Regression coverage: nearest-before-limit, new active station visibility, pending station exclusion, changed customer origin, missing location, coordinate validation (including zero), fuel filtering, and cancellation of stale background responses after location changes.

## Final acceptance — 2026-10-10

This section supersedes the earlier baseline verification counts above. The release adds migrations 026–031: transactional public support linkage, independent notification visibility, durable intake/support email outbox, station publication review, redacted business activity, restricted partner API keys and the missing card payment processor reference. Public support and sales inquiries, job applications, privacy requests, paid-plan services and partner operational requests persist to backend queues. Admins can review records, reply, download protected attachments, publish jobs, approve stations and inspect financial lifecycle records. Financial lifecycle rows are events, not a revenue total: do not add a checkout and its later confirmation as separate income. Audit database triggers are transactional and use allowlisted metadata; sensitive identities, passwords and API keys are excluded. HTTP review actions record the actor separately.

Partner API access is available only to an active catalog plan advertising it and an active owner/admin membership. Tokens are shown once, stored only as SHA-256 hashes, expire within 90 days, and authorize specified read-only endpoints for their organization. Revocation, subscription expiry and membership removal invalidate access. Admin staff role labels describe duties; they do not imply granular permissions—each admin currently has full platform administration access.

Support/intake email queue status `accepted` means the provider accepted the message, not that it reached an inbox. Retry uses the same idempotency key. Ambiguous attempts older than 23 hours require operator/provider reconciliation before another send. Resend documents a 24-hour idempotency window: https://resend.com/docs/dashboard/emails/idempotency-keys. Standard notification, OTP and other direct mail paths remain governed by their existing provider delivery behavior. A scheduler must be running for unattended queue retries and payment reconciliation. Private Supabase upload buckets and valid storage credentials are required for resumes/support attachments.

Admin dispute decisions cannot fabricate a wallet credit. Original-payment refunds use Support & Settlements and the existing payment refund workflow. Manual payouts, physical card delivery and biometric authorization remain explicitly coming soon. Plan service requests are operations coordination requests; an included benefit does not promise automatic booking or confirmed vendor availability.
